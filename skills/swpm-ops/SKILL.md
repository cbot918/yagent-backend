# SWPM Ops
操作 eai-erp 軟體專案後台的手冊：盤點、派工、交接、驗收，以及誰在哪一關負責什麼。

## 何時用
盤點專案狀況、指派任務、推動「實作→測試→驗收」這條線，或要判斷某件事該找誰時。

## 三階段與分工

| 階段 | 預設任務 | 誰做 | 帳號 |
|---|---|---|---|
| 1 設計 | 需求釐清 / 介面流程設計 / 技術方案評估 | SA | `sa@agent.local` |
| 2 開發 | 實作、code review | Engineer | `engineer@agent.local` |
| 2 開發 | 測試 | QA | `qa@agent.local` |
| 3 上線 | 部署 / 驗收 / 文件與交接 | SA（驗收）、DevOps（部署） | `sa@agent.local` |

一個功能 = 一張**主任務**，底下開子任務分給不同角色。子任務不填負責人／截止日就**繼承主任務**的——所以主任務設好截止日，整條線就都有期限了。

## 派工的鐵則：寫進系統 + 真的請人做

```
create_sw_task(assigneeEmail=…)   ← 留下記錄（前端看得到、逾期算得到）
delegate_to_role(roleId, task)    ← 真的讓那個角色跑一輪
update_sw_task(status=…)          ← 回寫結果
```

- 只做第一步 = 紙上作業，沒人真的動工。
- 只做第二步 = 事情做了但系統上查不到，逾期告警也不會亮。
- **BLOCKED 一定要寫 `blockedReason`**，後端會擋掉沒原因的卡關。原因要寫「在等什麼」，不是「還沒好」。

## 交接靠留言，不靠轉述

每一關做完，把產出用 `add_sw_comment` 貼在**那張任務**上。下一關的人用 `list_sw_comments` 讀。理由：留言在 ERP 裡是永久記錄，人在 `/swpm` 頁面看得到；而 chat 裡講過的話，下一個角色的 session 看不到。

**QA → SA 的交接格式**（QA 產出，SA 消費）：

```
驗收清單
1. 建立報價單 / POST /api/quote/quotations/fromSpec，body {...} / 回 200 且有 quoteNo
2. 分享頁可開 / GET /share/quote/<token> / 頁面出現客戶名，且看不到成本欄位
3. ...
```

每項三段式：**功能名 / 怎麼呼叫（URL＋方法＋輸入）/ 期望結果**。挑真正代表這個功能的 3～7 項，不要逐行覆蓋——這是「重點驗收」不是回歸測試。

## 什麼情況不准放行（QA 專用）

QA 的價值在於**擋下不該過的東西**，不是回報「大致上可以」。以下任一情況成立，任務就**不准標 DONE**，要標回 `IN_PROGRESS` 或 `BLOCKED` 並寫清楚原因：

- **任何 5xx**。使用者輸入格式不對就回 500 是缺陷，不是「建議改善」——正確行為是 400。看到 5xx 一律擋。
- 未處理的例外（stack trace 出現在 server log 裡）。
- 資料寫壞、寫到錯的地方，或該回滾沒回滾。
- 權限沒擋住該擋的人。

**不准自己把等級降成「不影響驗收」。** 你可以說「這不阻擋主要流程」，但要不要放行是回報給 swpm 的判斷題，不是你單方面下的結論。真的只是建議性質的（命名、註解、可讀性），才寫在「附帶建議」。

## 沒驗收完不准標 DONE（swpm 專用）

三段流水線只要有一段沒跑完，任務就**不是** DONE：

- engineer 交付 → 頂多 `IN_PROGRESS`
- qa 測完 → 還是 `IN_PROGRESS`
- **sa 驗收通過** → 才可以 DONE

**流程不准中途停。** 如果你在一輪之內跑不完三段（迭代次數會用完），不要假裝結束——明確講「已完成 1、2，第 3 段 sa 驗收尚未執行」，並把任務留在 `IN_PROGRESS`。使用者看到 DONE 會以為驗收過了，那是最糟的失真。

## 不要叫 coding agent 去啟動伺服器

`dispatch_coding_task` 是**一次性、會結束**的呼叫；長駐的 dev server 不會結束。而且 harness 的 sandbox 不准綁 port（codex 回 `listen EPERM`），所以那條路本來就走不通。

要驗收就先確認服務已經在跑；沒在跑就回報「需要有人先啟動 <服務> 在 <port>」，然後停下來等，**不要試圖自己啟動**。可以請 coding agent 做的是 build、跑測試、改檔案這種會結束的事。

## SA 的 E2E 驗收

SA **不看程式碼**。流程是：`list_sw_comments` 讀清單 → 翻成 `smoke_check` 的 `checks` 陣列（**一次呼叫跑完整份清單**，不要一項一次）→ 看實際回應判斷。

- 能明確斷言的填 `expectStatus` / `expectContains`，拿 PASS/FAIL。
- 不好斷言的（畫面對不對、文案通不通）就不要填期望，直接讀 `smoke_check` 回傳的內容自己判斷。
- UI 類的檢查用 `mode: "page"`，會回**渲染後**的文字。
- 判斷標準是**功能面與使用者面**——「這是不是當初規格要的東西」。程式碼品質是 QA 與 code review 的守備範圍。
- 驗收完 `add_sw_comment` 回寫：通過／不通過、不通過是哪一項、實際看到什麼。不通過就把任務改回 `IN_PROGRESS` 或 `BLOCKED`，別讓它停在 DONE。

`smoke_check` 只打得到 `E2E_ALLOWED_ORIGINS` 裡的網域。打不到就是環境沒設，回報「無法驗收」比猜結果好。

## 回報習慣

- 先查再說：`list_sw_projects` / `query_sw_tasks` 拿到的進度、逾期、健康度是後端算的，直接引用。**不要自己推估，也不要編任務 id。**
- 報告先講「要注意什麼」（逾期、卡關、沒人認領），再講細節。
- 不要把整份任務清單原樣倒給使用者——那是工具輸出，不是報告。
