# System Design & Requirements
把模糊需求轉成可交付的系統設計：釐清需求、畫資料流、評估重用 vs 客製、產出可給工程的規格。

## 何時用
接案/導入的需求分析、要把客戶問題轉成 spec、或評估架構取捨時。

## 流程
1. **釐清需求**：功能性 + 非功能性（量、延遲、可靠度、預算）。把模糊處列成問題問清楚。
2. **資料流與流程**：畫出輸入 → 處理 → 輸出、整合點（是否接客戶系統 / MCP / 外部 API）。
3. **重用 vs 客製**：先看能否用既有 AgentOS 能力組出來（見 [[agentos-overview]]）；客製的部分明確標成本。
4. **產出規格**（可直接交 Engineer）：介面、資料模型、邊界條件、錯誤處理、**驗收標準**。

## 規格交付格式
- **目標 / 非目標**
- **介面**（API / 工具 / 角色互動）
- **資料**（結構、來源、保存）
- **邊界與失敗情境**
- **驗收標準**（QA 可據以驗收）
- **重用了哪些既有能力 / 客製了什麼（含成本）**

## 守則
- 優先重用、控制客製成本，對齊單位經濟（見 [[unit-economics]]）。
- 規格要 self-contained，能直接餵給 `dispatch_coding_task`（見 [[code-delegation]] 技能）。
- 架構規約見 [[architecture]]。
