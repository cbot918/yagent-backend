# 單位經濟與定價基準（給 CFO / Sales / SA）

> 報價、接案、定價的共用算盤。策略守則見 [[company-plan]]；成本計量機制見 [[architecture]] 的 usage/budget。

## 1. 核心原則

- **每個提案都問**：單位經濟（unit economics）與回收期。
- 直接成本一定要含 **LLM + coding harness 用量**（這是隱形成本，最容易被低估）。
- **不接虧本案**：報價 < 直接成本 + 應分攤的維運/人力，就不接，或重新劃 scope。

## 2. 三條變現線的成本結構

| 線 | 收入 | 主要直接成本 | 毛利特性 |
|---|---|---|---|
| 內容/社群（短期） | 業配/課程/訂閱 | 內容產製工時、少量 LLM | 低直接成本，但靠量與信任累積 |
| 產品 AgentOS（中期） | SaaS 訂閱/導入費/用量計費 | 每用戶 LLM+harness 用量、客服 | 用量計費要把成本轉嫁，否則越用越虧 |
| 顧問/接案（長期） | 專案費/顧問費 | 人力工時 + 該案 LLM/harness 用量 | 高毛利，但要沉澱成可複用能力才划算 |

## 3. 接案報價檢查清單

1. 估該案的 LLM/harness 用量（開發期 + 上線後每月）。用 `billing.json` 的價表與 `.usage` 歷史抓基準。
2. 一次性（開發） vs 經常性（每月維運/用量）分開報。
3. 設預算上限（對應 AgentOS 的 budget 子系統）寫進合約，避免用量失控吃掉毛利。
4. 標明：客製範圍、可複用沉澱、驗收標準、超出 scope 的計價方式。

## 4. 定價心法（對小老闆）

- 以「省下的成本/時間」或「帶來的營收」定錨，不以「token 數」定錨。
- 「可控成本」本身是賣點：讓客戶看到 budget 面板 → 願意付安心費。
- 訂閱層級用「能用幾個 AI 員工 / 每月用量額度」切，簡單好懂。
